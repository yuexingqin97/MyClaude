# 大衍决 (Myriad Mind) — 开发回顾与未来展望

> 📅 2026-05-31 | 从 v0.1 到 v2.1 的完整演化史

---

## 一、项目起源

2026 年 5 月，我在学习 Bevy ECS 时发现一个痛点：看视频教程做笔记太费时间——下载→转字幕→截图→整理→写总结，一个 55 分钟视频要花 2-3 小时。于是 fork 了 [imlewc/video-to-subtitle-summary-skill](https://github.com/imlewc/video-to-subtitle-summary-skill)，开始魔改。

最初的 skill 只是一个简单的"视频链接入→字幕+摘要出"的 pipeline，大概 200 行 SKILL.md。今天大衍决的 SKILL.md 已超过 3000 行，覆盖 8 种输入模式、30+ 功能特性、10 个配置开关。

## 二、迭代历程

### v0.1 — 奠基（2026-05-20）

**做了什么：** Fork 上游项目，搭建本地环境（Python 3.12 / FFmpeg / faster-whisper / yt-dlp），跑通第一条 B 站视频。

**核心能力：** 下载视频 → 提取音频 → faster-whisper 转写 → Claude 生成摘要。

**关键决策：** 选择 faster-whisper 作为默认 ASR 后端（免费、本地、中文识别尚可），而非直接调云服务 API。

---

### v0.2 — 关键帧 + 翻译（2026-05-21）

**新增：**
- 步骤 3.5：ffmpeg 按间隔截取关键帧（`extract_keyframes.py`）
- 步骤 6：英文视频自动翻译为中英对照
- 步骤 7：生成结构化 Markdown 学习笔记

**教训：** 截图最初集中放在"关键画面"章节，阅读体验很差——读者看到截图时已经忘了对应的文字内容。后来改成**内嵌到知识点旁边**，体验大幅提升。

---

### v0.3 — 可点击时间戳 + 截图规则（2026-05-22）

**新增：**
- 时间戳可点击（B 站 `?t=秒数`、YouTube `&t=秒数`）
- 截图选择规则：字幕交叉校验（截图时间戳 ↔ SRT 同时间段内容）
- 只保留用到的截图，删除多余文件

**设计精髓：** 截图决策从"看画面"升级为"看画面+看字幕"——讲师在闲聊时截的 PPT 封面会被过滤掉，因为字幕无实质内容。

---

### v0.4 — 文章模式 + Mermaid 图表（2026-05-23 ~ 05-25）

**新增：**
- Mermaid 图表自动绘制（架构图/流程图/时序图/状态图/类图）
- 文章学习模式（知乎/CSDN/Wiki 等 URL）
- 扩展学习资源推荐（官方文档/相关视频/知乎/GitHub/Wiki/社区）

**关键认知：** 纯文字笔记单调，Mermaid 把抽象关系可视化后信息密度大增。但 Mermaid 有坑——`|` 是关键字、`<br/>` 在 quoted 标签里不解析，踩过好几轮。

### v0.5 — 评论 + 可靠性 + 元信息（2026-05-26 ~ 05-27）

**新增：**
- 评论区精华提取（B 站 curl / YouTube yt-dlp）
- 阅读时长 + 难度评级（🌱🌿🌳）+ 可靠性评级（🟢🟡🟠🔴）
- 文档元信息（生成时间/模型/Token/版本号+更新日志）

**设计决策：** 可靠性评级不是"打分批判创作者"，而是"帮助读者分辨哪些需要自行验证"——标注而非批判，小口误不扣分。

### v0.6 — 改名大衍决（2026-05-28）

**背景：** 原名字 `video-to-subtitle-summary` 又长又干，而且不止处理视频了。

**新名由来：** 凡人修仙传中韩立的**大衍决**——神识分裂多股各自运转。隐喻：一个链接丢进去，拆解为摘要/笔记/图表/术语/资源多路并行输出。英文名 `myriad-mind`（万千神念）。

**改动量：** 目录改名、全部脚本路径更新、README 重写、记忆文件重建——约 20 个文件。

### v2.1 — 截图系统改良（2026-05-31）

**背景：** v2.0 虽然有截图功能，但存在两个瓶颈：①固定间隔截图不感知内容变化，关键帧容易漏截；②截图嵌入质量不可追溯——不知道哪些截图被用了、为什么被选/被跳过。

**核心改进：**

- **字幕引导截图（🎯引导机制）：** 在 ASR 完成后分析字幕内容，识别"代码展示/架构图/配置/运行结果/对比讲解"等关键画面类型，反向推导最佳截图时间点。不再是机械的固定间隔，而是让字幕内容"告诉"系统哪里该截。
- **结构化截图审查：** 每张候选截图经过三道审查——来源标记（🎯引导 / 🔍场景补充 / ⏱️保底）、质量评分（1-3）、选中/跳过原因记录。
- **截图审计追踪：** 完整记录从候选→审查→嵌入→跳过的决策链路，让每张截图都有"出生证明"。
- **评论区精华：** 自动获取视频评论（B 站 API / YouTube yt-dlp），筛选高价值讨论，附跳转链接嵌入笔记。
- **代码示例嵌入：** 在关键概念旁附带可复制运行的代码块，不再只是文字描述。

**效果量化（以 LearnEcs 同一视频为例）：**

| 指标 | v2.0 | v2.1 | 变化 |
|------|:--:|:--:|------|
| 截图候选 | ~30 帧（固定间隔） | 28 帧（字幕引导） | 更有针对性 |
| 截图选中 | 2 张 | **12 张** | +500% |
| 截图审查 | ❌ 无记录 | ✅ 27→12（15 张跳过有据可查） | 质量可追溯 |
| 代码示例 | 几乎无 | 大量 Rust 代码块 | 可复制运行 |
| 评论区 | ❌ 无 | ✅ 2 条精选 + 编辑注 | 新增 |
| 调试追踪 | 简单耗时表 | 完整审计链（流水线耗时 + 截图来源表格 + 跳过原因 + 决策链路图） | 排查从猜→读 |
| 生成耗时 | ~3.5 分钟 | ~12 分钟 | 3.4× |
| Token 消耗 | ~52K | ~75K | +44% |

**关键认知：** 截图不在于多，而在于"每张都有明确的嵌入理由"。v2.0 截图少是因为筛选粗放——不确定该截哪帧，就保守地少截。v2.1 的引导机制让系统从"被动等帧"变成"主动找帧"，审查机制让质量从"靠感觉"变成"可审计"。

## 五、关键设计决策回顾

### 1. 为什么是 Skill 而不是独立 App？

**决策：** 基于 Claude Code Skill 框架，Markdown + Bash 脚本。

**理由：**
- 开发成本极低（无需 UI、无需后端、无需部署）
- Claude 本身就是最强"大脑"，不需要自己训练模型
- Skill 框架提供工具链（Read/Write/Bash/WebFetch），开箱即用
- 验证想法只需改 Markdown，迭代速度极快（改完即生效）

**代价：** 依赖 Claude Code 平台，无法脱离 Claude 独立运行。

### 2. 为什么用修仙主题？

**决策：** 所有命名（大衍决/修为面板/灵根图谱/炼气筑基）统一修仙世界观。

**理由：**
- 学编程和修仙本质相似：长期积累、突破瓶颈、越学越深
- 枯燥的工具加上叙事层 → 用户粘性大增
- "再写 1 篇就能突破筑基期"比"完成 5 篇笔记"更有驱动力

### 3. 为什么不自己训练模型？

**决策：** 100% 依赖 Claude API，不 fine-tune、不本地推理。

**理由：**
- Claude 的理解/总结/翻译/画图能力已经足够好
- Fine-tune 需要大量标注数据，ROI 极低
- ASR 用 faster-whisper 是例外——这是硬需求，且开源方案成熟

### 4. 截图策略的演化

**v0.2-v2.0（固定间隔时代）：** ffmpeg 固定间隔截图 + Claude 交叉字幕筛选。简单可靠，但关键帧容易漏截——固定间隔不感知内容变化。

**v2.1（字幕引导时代）：** ASR 完成后分析字幕内容，识别关键画面类型（代码展示/架构图/操作演示），反向推导最佳截图时间点。从"被动等帧"变成"主动找帧"。

**为什么不用 AI 场景检测？**
- AI 检测"有意义帧"本身消耗 token
- 字幕引导 + Claude 审查的效果已经足够好，且可审计
- 简单方案出问题容易排查——每张截图的来源和跳过原因都有记录

### 5. 为什么配置项这么多？

**决策：** 20+ 配置项，全部默认开启，可按需关闭。

**理由：**
- 不同场景需求差异巨大（快速笔记 vs 深度学习）
- 配置开关 = 用户可控的"省流模式"
- `.env` 文件比命令行参数更适合持久化偏好

## 六、未来：如果做成独立 App

### 可行性分析

| 维度 | 评估 |
| --- | --- |
| **技术可行性** | ⭐⭐⭐⭐⭐ 核心能力已验证，Claude API 足够强 |
| **市场需求** | ⭐⭐⭐⭐ 知识管理+AI 笔记是刚需 |
| **竞争壁垒** | ⭐⭐⭐ 功能领先但易被复制 |
| **商业模式** | ⭐⭐⭐ 订阅制可行，但需证明独特价值 |

### App 形态设想

```
大衍决 App
├── 输入层：分享链接 → 自动识别 → 炼化
├── 笔记层：Markdown 渲染 + Mermaid + 截图库
├── 面板层：修为面板 + 成就 + 等级
├── 社区层：分享笔记、对比、发现热门
└── 复习层：间隔重复、每日一修、Anki 导出
```

### 技术栈推演

- **前端：** React Native / Flutter（跨平台）
- **后端：** Go / Rust（Claude API 代理 + 用户系统 + 任务队列）
- **存储：** PostgreSQL（笔记元信息）+ S3（截图/缓存）
- **AI：** Claude API（核心推理）+ faster-whisper（ASR）
- **成本：** 单人月费 $15-20 可覆盖 API + 服务器成本

### 核心挑战

1. **Claude API 成本**：一篇 55 分钟视频消耗约 5-8 万 tokens（~$0.75-1.2），需要做智能缓存
2. **视频下载合法性**：B 站/YouTube 的版权问题需要谨慎
3. **用户留存**：笔记生成是"一次性"需求，需要持续价值（复习/社区）来留存

### 间接竞品

| 产品 | 关联 | 差异化 |
| --- | --- | --- |
| **Notion AI** | 笔记+AI | 通用笔记，非学习专用 |
| **Obsidian + Copilot** | 本地知识库+AI | 插件生态强，但无视频处理 |

### 大衍决的差异化

2. **视频原生**：关键帧+时间戳+评论区，视频学习体验无竞品对标

## 九、反思与总结

### 做对了什么

1. **先跑通再优化**：第一版只用了 2 天就跑通了 B 站视频全流程，后续每次迭代都是可用状态
2. **命名很重要**：从 `video-to-subtitle-summary` 到 `myriad-mind`（大衍决），不只是改名字，是重新定义了产品定位——从工具到身份
3. **配置化而非硬编码**：20+ 配置项让 skill 从"我的工具"变成了"可分发的基础设施"
4. **修仙叙事**：枯燥的 CLI 工具加了世界观之后，学习和分享的意愿完全不同
5. **调试友好**：`DEBUG_METADATA` 的分步追踪让排查问题从猜谜变成了读日志；v2.1 的截图审计追踪把"为什么选了这张"也纳入可追溯范围

### 做错了什么

1. **前期没做标签系统**：笔记多了才发现搜索靠 `grep` 太原始，应该在 v0.5 就加
2. **模板语法坑**：Mermaid `|` 和 `<br/>` 的问题踩了 3 次才记住
3. **缓存路径泄露**：第一版笔记把 `/tmp/video_analysis/` 写进了元信息，不够专业
4. **文档滞后**：功能加了很多，但 README 和记忆文件更新不及时
5. **版本号混乱**：LearnEcs 两份笔记都标 v2.0，缺乏区分——应该在文件名或元信息中标明 skill 版本

### 如果重新做

- 第一天就定义好输出格式模板（阅读信息+标签+元信息）
- 先做修为面板再做内容生成（有统计才有动力）
- 配置项从第一天就用中英双语注释
- 截图系统一开始就用字幕引导而非固定间隔

### 最后

从一行 `ffmpeg -i video.mp4 audio.mp3` 开始，到 3000 行 SKILL.md、9 种模式、30+ 功能、20+ 配置项。大衍决已经从一个"帮我看视频"的小脚本，变成了一个完整的 AI 知识管理系统。

大衍决的迭代有一个清晰的演化主线：**让每一篇笔记的质量可度量、可追溯、可复现**。v0.x 解决了"能不能生成"，v2.0 解决了"够不够完整"，v2.1 解决了"好不好审计"——截图从 2 张到 12 张只是表象，真正的进步是每张截图都有了来源标记、质量评分和跳过原因。

如果说有什么最意外的收获——**修仙叙事**。本以为只是一个命名彩蛋，结果它成了整个系统的灵魂：成就驱动行为、等级给予反馈、面板展示成长。一个好的叙事，比十个好功能更让人愿意留下来。
